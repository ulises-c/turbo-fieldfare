# Qwen 3.6 35B-A3B Support on the Fork — Implementation Plan

> **For Hermes:** planning artifact only. No source was edited to produce this
> (AGENTS.md scope rule). Execute task-by-task after the blocking questions in
> §7 are answered.

**Goal:** Add Qwen 3.6 35B-A3B as a second supported architecture on
`ulises-c/turbo-fieldfare`, based on upstream PR #29, rebased onto current
`upstream/main`, with NVMAI's optimizations evaluated separately and only
adopted on our own measurements.

**Architecture:** Take PR #29 as the base — it is the only clean,
review-shaped port. Rebase it onto current `upstream/main` (the hard part,
scoped in §3). Treat PR #105 / NVMAI as an *optimization quarry*, not a merge
source: cherry-pick individually attributable perf commits one at a time,
behind opt-in flags, each with a matched-control A/B.

**Tech Stack:** Swift 6.2, Metal, SwiftPM. Host: MacBook Pro M5 Max, macOS 26+.

All facts below were verified locally against `upstream`, `pr29`, and a
depth-400 fetch of `Pummelchen/NVMAI`.

### PR #29 — `NeelM0906:qwen36-support`

| Property | Value |
| --- | --- |
| State | OPEN, `mergeable: CONFLICTING` |
| Size | 76 files, +6,941 / −530 |
| Base | forked at `f8abc44` ("Speed up long-context prefill on Apple10 (#16)") |
| Drift | 29 upstream commits landed since; PR has 27 of its own |
| Head | `bddb8e5` |

This is a genuine second-architecture port, not a bolt-on. It introduces a

a `GDNStateManager` (fixed recurrent state instead of per-token KV on 30 of 40
layers), a ChatML tokenizer dialect, and installer/CLI/server/app plumbing.
Gemma 4 is claimed byte-identical, and the manifest is backward compatible
(missing `arch.family` ⇒ Gemma 4).

### PR #105 — `Pummelchen:NVMAI`

| Property | Value |
| --- | --- |
| State | OPEN, `mergeable: CONFLICTING` |
| Size | 574 files, +60,414 |
| Body | explicitly "a pointer to the fork; the full code lives there" |

**Critical structural finding:** `git merge-base --is-ancestor pr29 nvmai/main`
returns true. **NVMAI contains PR #29 in full.** It is PR #29 plus 307
additional commits (569 files changed, +56,342 / −20,048 relative to pr29).

Of those changed files, **428 have `NVMAI` in their path** — the bulk of the
delta is a rebrand (`sources/`, `tests/` lowercase trees replacing `Sources/`,
`Tests/`), plus benchmark tooling, plus a *third* model family ("Ornith" /
Qwen3.8-Flash-Next) that is out of scope here.

**Conclusion: PR #105 is not a merge candidate.** Merging it would import a
rebrand, an old upstream base, and an unrelated model port. Its value is a
list of individually-attributable, individually-measured optimization commits
sitting on top of the same PR #29 code we want.

## 2. Recommended approach

```
fork-main (synced to upstream/main)
   └── feat/qwen36-arch          ← PR #29, rebased. Correctness only. PR #1.
         ├── perf/qwen-parallel-pread     ← NVMAI 4beb74f. PR #2.
         ├── perf/qwen-expert-slots-pin   ← NVMAI 069aed6. PR #3.
         ├── perf/qwen-moe-phase1-tg      ← NVMAI moe_phase1_xsh16. PR #4.
         └── fix/kernel-stats-moe-sampling ← NVMAI 927c94e. PR #5.
```

Rationale:

1. **Correctness lands separately from performance.** If the rebase and a perf
   flip ship together and Qwen decode is wrong, we cannot bisect the cause.
2. **One lever at a time with a matched control** — this is the stated
   preference for local-model work, and it is the only way to tell a real
   capacity gain from unified-memory headroom noise.
3. **Every perf pick is separately attributable.** Each NVMAI commit carries
   its own measurement in the message; we re-measure on M5 Max rather than
   inheriting an M3 24 GB number.
4. **Upstream may still rework PR #29's seam.** Keeping the arch plumbing as
   one reviewable branch means a rebase onto a revised upstream seam is a
   contained operation, not a 60k-line untangle.

### Explicitly rejected alternatives

- **Merge NVMAI/main directly.** Imports a rebrand, an unrelated model family,
  and a base that is 29+ upstream commits stale. Non-starter.
- **Wait for upstream to merge #29.** It has been CONFLICTING since Jul 31 with
  no reviewer assigned and no upstream engagement in the thread. Blocking on it
  is unbounded.
- **Re-implement the port from scratch.** ~7k lines of validated Metal kernel
  work including a CPU-reference-checked gated delta rule. No.

| `CLI/Run.swift` | 2 | 91 | #159 + #144 | medium |

### The dominant cause is one upstream commit

`fd3c0b8` — "Add optional Gemma 4 image support (#144)" — touches
`RealForwardRunner`, `Tokenizer`, `Args`, `OpenAIModels`,
`AppModelInstallDescriptor`, `AppModel`, and `Model.swift`: **exactly** the
files PR #29 rewires for family dispatch. This is not incidental. Both changes
generalize the same seams, in different directions (one adds a modality, one
adds a family).

**Design consequence:** resolution must produce a *two-axis* model descriptor —
family × modality — not a flat enum. Gemma 4 has vision; Qwen 3.6 does not.
Qwen must be `vision: unsupported` and fail closed on image input, matching the
existing "never accept an image and then answer as though it had not been
sent" rule in AGENTS.md.

### The one hard conflict, characterized

`RealForwardRunner.swift` hunk 2 (~190 lines). PR #29 wraps the prefill
attention block in `if isLinear { …GDN path… } else { …attention… }`. Upstream
`ec8ad21` (#159) *inside that same block* added the FP16-KV guard and the
`prefillAttentionPath` selection:

```swift
                                                  path: prefillAttentionPath)
            } else {
                throw PrefillError.chunkedUnsupported(
                    "chunked prefill attention requires FP16 KV")
            }
```

Resolution: **keep PR #29's three-way dispatch as the outer structure, then
re-apply upstream's guard and `prefillAttentionPath` inside the full-attention
branch.** Do not take either side wholesale — `-X ours`/`-X theirs` silently
drops one of the two behaviors here. Hunk 3 (2,378–2,545) is the same shape.

## 4. Task breakdown

### Phase 0 — Sync (5 min)

`fork-main` is currently 0 ahead / 2 behind `upstream/main`.

**Task 0.1** — Sync the integration branch.
```bash
git fetch upstream
git checkout fork-main && git merge --ff-only upstream/main && git push origin fork-main
```
Expected: fast-forward, 2 commits.

**Task 0.2** — Land or park `docs/record-256k-context-ladder`. It is clean and
pushed but unmerged; decide before branching so the Qwen work does not stack on
an in-flight docs branch.

### Phase 1 — Rebase PR #29 (the real work)

**Task 1.1** — Create the branch and stage the merge.
```bash
git checkout -b feat/qwen36-arch fork-main
git merge pr29    # expect 20 conflicts
```
Prefer `merge` over `rebase` here: PR #29 is 27 commits with internal
merge commits from worktree agents; replaying them individually multiplies the
same conflict 27 times.

**Task 1.2 – 1.13** — Resolve conflicts in dependency order, **committing after
each file group** (incremental commits, not one big resolution commit):
1. `Package.swift` — union both `resources:` arrays and both dependency lists.
2. Format/manifest: `GTurboJSON.swift`, `VerifiedInstallTool.swift`.
3. Repack: `Command/main.swift` — `--model` and `--vision-output` are
   orthogonal flags; reject `--model qwen36 --vision-output` explicitly.
4. Tokenization: `Tokenizer.swift`, `StructuredAssistantDecoder.swift`. Keep
   upstream's #118 incremental/lossless decode path *and* the ChatML dialect;
   verify the `<unk>` fallback fix (`7815cc1`) survives.
5. Runtime: `RealForwardRunner.swift` — per §3. Do this one alone, in one
   sitting, and diff the resulting Gemma path against `upstream/main` to prove
   it is untouched.
6. CLI: `Args.swift`, `Run.swift`, `CLIArgumentsTests.swift`.
7. Server: `OpenAIModels.swift`, `HTTPServer.swift`, `ServerArguments.swift`,
   `Command/main.swift`.
8. App: `AppModelInstallDescriptor.swift`, `AppModel.swift`, `MetalContext.swift`.
9. Docs: `README.md`, `docs/SYSTEM_DESIGN.md`, `docs/RUNTIME_CONTROLS.md`.

**Task 1.14** — Add the family × modality guard: Qwen 3.6 must reject image
input with a clear "image support is unavailable for this model" error at the
server ingress and the app, not silently drop it.

### Phase 2 — Verification gates

**Gate A — builds and unit tests, no model required.**
```bash
swift build -c release
Scripts/test.sh
ruby Scripts/check_markdown_links.rb
```
Expected: PR #29 claimed 570 tests / 114 suites. Our number will differ
(upstream added vision suites); what matters is **zero failures** and that the
pre-existing Gemma suites are unchanged.

**Gate B — Gemma 4 non-regression (the important one).**
Preflight per AGENTS.md: macOS 26+, Swift 6.2+, disk, `memory_pressure -Q`,
completed `scratch/gemma4.gturbo`, and no process matching
`pgrep -fl 'TurboFieldfareServer|TurboFieldfareMac|TurboFieldfareDecodeService|TurboFieldfareCLI|TurboFieldfarePackageTests|swiftpm-testing-helper|mlx_lm|mlx-lm'`.

Then greedy-decode the three frozen `real-generation-v1` prompts at fixed seeds
on `fork-main` and on `feat/qwen36-arch` and assert **byte-identical output**.
Anything less than byte-identical is a blocking defect, not a rounding
difference.

**Gate C — Qwen install and first token.**
```bash
swift run -c release TurboFieldfareRepack --model qwen36 --output scratch/qwen36.gturbo
```
~19.6 GB download, ~19.6 GB installed (vs Gemma's 14.3 GB). Confirm disk
headroom first. Use `--resume` on interruption; never duplicate the Gemma
`.gturbo`.

**Gate D — Qwen benchmark, community protocol, unmodified.**
Follow `docs/COMMUNITY_BENCHMARKS.md` exactly: three frozen prompts, fixed
seeds, temperature 0.2 / Top-K 64 / Top-P 0.95, 4K context, 16 expert-cache
slots, one discarded warmup, one measured run per case in a fresh process. No
experimental controls, no profiling. Record commit, hardware/RAM, macOS, Swift
version, exact command, exit code, and the complete timing footer.

### Phase 3 — Optimization picks (only after Phase 2 is green)

Candidates, in descending value-per-risk. Each gets its own branch, its own
A/B against `feat/qwen36-arch` as the matched control, on an otherwise idle
machine, alternating runs.

| # | NVMAI commit | Change | Their claim | Risk |
| --- | --- | --- | --- | --- |
| 1 | `927c94e` | fix `KERNEL_STATS` MoE undersampling (recorded 0.33 ms/token vs true 14.4) | instrumentation correctness | **low — do this first** |
| 2 | `4beb74f` | parallelize expert pread fills across idle CPU cores | +28% decode | low; verify byte-identical greedy |
| 3 | `069aed6` | 64 expert slots + `mlock` resident weights | +10% | **medium — changes memory contract** |
| 4 | `9e45448`-era | MoE phase-1 threadgroup-staged rewrite (`moe_phase1_xsh16`) | routedCB −36% | medium — Metal kernel |
| 5 | — | `F_RDADVISE` read-ahead default | +10.6% | low, already a knob |
| 6 | — | 4096-token prefill chunks | ~3.2× TTFT | low |

**Pick #1 first and independently.** If NVMAI's profiler was undersampling MoE
by 40×, every downstream NVMAI attribution was made against a broken profile.
Landing the instrumentation fix before any perf pick means our own A/Bs are
measured on a correct instrument.

**Hard constraints on Phase 3:**
- All NVMAI numbers are M3 24 GB. We are on M5 Max. Treat every claim as a
  hypothesis to test, not a result to inherit.
- Picks #3 and #6 flip *defaults*. AGENTS.md forbids changing runtime defaults
  unprompted. Land them as opt-in flags; propose a default flip only with our
  own measurements attached.
- Pick #3 explicitly trades against the bounded-memory contract — NVMAI found
  128 slots net **−6%** on a 24 GB host. Re-derive the slot sweep on M5 Max
  rather than copying `64`.
- NVMAI is Apache-2.0 and a declared fork; cherry-picks must preserve
  authorship (`git cherry-pick -x`) and keep `André Borchert` / `Qwen-Coder`
  trailers. Add `THIRD_PARTY_NOTICES.md` attribution.

## 6. Risks and tradeoffs

1. **Upstream reworks the family seam.** PR #29 has no reviewer and no upstream
   engagement since Jul 31. If `drumih` lands a different discriminator, we
   rebase. Mitigation: keep arch plumbing in one branch; do not scatter it.
2. **The `RealForwardRunner` merge is genuinely hard.** 365 conflicted lines in
   the hottest file, where upstream's prefill work and PR #29's layer dispatch
   overlap structurally. Gate B (byte-identical Gemma) is the only real defense.
3. **Two independent generalizations of the same seam.** Vision (#144) and
   family (#29) both widen the model descriptor. Merging them naively produces
   a combinatorial mess; §3's two-axis descriptor is the containment.
4. **Disk.** Gemma 14.3 GB + Qwen 19.6 GB ≈ 34 GB of `.gturbo` plus the
   `.build` release tree. Verify before Gate C.
5. **Untested surface inherited from PR #29:** vision omitted, acceptance
   evidence only at 4K context, server tool-call loop unit-tested but never
   exercised live, 8 GB figure is emulated pressure not real hardware. We
   inherit all four caveats and must restate them, not quietly drop them.
6. **Qwen decode is expert-I/O bound (53% of the token on their host)** and
   slower than Gemma on comparable hardware. PR #29 is explicit that the cause
   is a *hypothesis*, not a finding. Do not repeat it as fact.

## 7. Blocking questions

1. **Scope of PR #1** — arch plumbing + CLI + repack only, or include the Mac
   app and server wiring in the same PR? (Recommend: all of PR #29 as one unit;
   splitting it means re-resolving the same conflicts twice.)
2. **Upstream contribution** — do we push the rebased branch back to
   `drumih/turbo-fieldfare` as a refreshed PR (credited to NeelM0906), or keep
   it fork-local? A rebased-onto-main PR #29 is materially more useful to
   upstream than the current CONFLICTING one.
3. **Phase 3 appetite** — land Phase 1–2 and stop, or commit now to the
   optimization sequence? Phase 3 is ~4 more A/B cycles with real model runs.
4. **`docs/record-256k-context-ladder`** — merge to `fork-main` before
   branching, or leave parallel?
5. **Qwen at long context** — PR #29's evidence stops at 4K. Given the existing
   256k context-ladder harness, do we extend it to Qwen (its 30 linear layers
   have a *fixed* recurrent state, so it should scale far better than Gemma)?
   This is arguably the most interesting result available here.
